# Registry-Command Injection Seam for the help schemas Drift Guard

Source: project-doc-review on 2026-05-27
Category: design
Location: 02-project-cli-contract-alignment.md (CLI Contract Alignment) — Implementation Plan step 7, Requirement 6, Acceptance Criteria

## Goal

Enable the `start help schemas` drift-guard test to assert each `--json`-capable command's real output shape offline, deterministically, without reaching the live CUE Central Registry. This is a prerequisite for the CLI Contract Alignment project's Requirement 6 acceptance criterion ("A test asserts each command's real `--json` output matches its documented shape"). The parent project's drift guard cannot be built until this seam exists.

## Scope

In scope:
- A registry-client injection seam that lets tests supply a stub client (via a small interface) to the registry-backed `--json` commands: `library`, `search`, `update`, `doctor`. The stub serves canned `FetchIndex` / `Fetch` / `ResolveLatestVersion` responses; production returns `registry.NewClient()`.
- Routing those commands' registry interactions through the provider so production behaviour is unchanged while tests can run them offline. This covers `doctor`'s schema-fetch path as well as its version-resolve path — `doctor --json` has two independent registry interactions and both go through the provider.
- A coverage strategy for `doctor validate`, whose `--json` output is produced by fetching and schema-validating every module in the index (not by reading the index alone).

Out of scope:
- The drift-guard test content itself and the `help schemas` topic — those belong to the parent project and are written once this seam is in place.
- `list`, `config get`, `config list`, `config settings` — these emit `--json` from local config with no registry dependency (`list` touches the registry only under `--verbose`, which the guard does not pass). They need no seam.
- Changing what `internal/cache` stores. It deliberately caches a version string, not index content; that stays.

## Current State

The parent project's Plan step 7 assumes two mechanisms that do not work against the current code:

1. It assumes `setupStartTestConfig(t)` with `skipRegistry: true` stops the registry-backed commands from dialing the registry. It does not. `skipRegistry` is a field on the `resolver` struct (`internal/cli/resolve.go:59`), consulted only in `resolver.ensureIndex()` (`resolve.go:674`). The registry-backed commands do not go through the resolver — they construct their own client. AGENTS.md states the scope precisely: skipRegistry applies "in tests touching the resolver."
2. It assumes a "local cached-index fixture (via `internal/cache`)" lets those commands "emit a shape offline." It cannot. `internal/cache` stores only a version string (`WriteIndex(version string)`, `ReadIndex().Version`). It short-circuits version resolution; the index content is still fetched from the registry (or CUE's on-disk module cache) by `FetchIndex`/`Fetch`.

How the commands acquire the index today:

| Command | Acquisition site | Notes |
| ------- | ---------------- | ----- |
| `update`, `install` | `fetchIndex(ctx, cmd, prog, msg)` in `internal/cli/modules_shared.go:26` | Already centralized. Returns `(*registry.Index, *registry.Client, error)`. Calls `registry.NewClient()` then `client.FetchIndex(...)` then `cache.WriteIndex(...)`. |
| `search` | `internal/cli/search.go:167` | Inline `registry.NewClient()` + `client.FetchIndex(...)`. Graceful fallback: registry errors degrade to local-only results. |
| `library` | `internal/cli/library.go:68` | Inline `registry.NewClient()` + `ResolveLatestVersion` + `Fetch`. Has an `--export` branch that dumps raw CUE; the `--json` path needs the parsed index. |
| `doctor` | `internal/cli/doctor.go:218` and `:274` | Two inline `registry.NewClient()` calls: one for schema validation, one for the index check. Reads `cache.ReadIndex()` only for the version. |
| `doctor validate` | `internal/cli/doctor_validate.go:196` | Inline `registry.NewClient()`, then `validateIndex` and `validateModules` → `validateOneModule` (`:646`) which calls `client.Fetch` per module and schema-validates each. |

There is no existing seam to inject a fake registry or index into any of these commands. `internal/cli/snapshots_test.go` exercises only text-mode `describe`/`config get`; it does not capture `--json` output. The test helper is `setupStartTestConfig` (see `internal/cli/config_testhelpers_test.go`).

The cost is asymmetric. `update`/`install`/`search`/`library`/`doctor` make shallow registry calls — index acquisition, version resolution, or fetching the schema module — all stubbable behind a single client provider. `doctor validate` is deep — it fetches and validates every module in the index per run, so making it emit a `--json` shape offline requires stubbing the per-module fetch/validate path, not just the client.

## Requirements

1. The registry-backed `--json` commands `library`, `search`, `update`, and `doctor` obtain their registry client through a single injectable per-instance provider that defaults to `registry.NewClient()` in production and can be replaced in tests with a stub. The existing `fetchIndex` helper acquires its client from the provider; `doctor`'s separate schema-fetch (`fetchAndValidateSchemas`) and version-resolve (`resolveIndexVersion`) calls do the same.
2. With the provider stubbed, each of those four commands runs under `--json` offline (no network, no live registry) and produces its documented output shape deterministically. The provider covers `doctor`'s schema-validation section as well as its index/version check.
3. Production behaviour of all four commands is unchanged: same index source, same `cache.WriteIndex` side effects (preserved at every existing call site — `fetchIndex` for `update`/`install`, `search.go:175`, `library.go:95` — and `doctor`'s `resolveIndexVersion` continues to read-only the cache, neither writing nor inheriting a new write), same graceful-degradation semantics (notably `search`, which must still fall back to local-only results when the registry is unavailable, and `doctor`'s schema validation, which must still fall through to a "Skipped" section when the registry is unreachable). `library` keeps its current structure (`ResolveLatestVersion` + `Fetch` + `cache.WriteIndex` + branch on `--export`/`--json`/text) because the `--export` branch needs `result.SourceDir` that the parsed-index seam would discard; the only change is that `library` obtains its client from the provider instead of calling `registry.NewClient()` directly.
4. `doctor validate` is covered by a separately-gated integration test that exercises the real registry path and asserts its `--json` shape (`ValidateReport` / `ValidateCategoryResult` / `ValidateModuleResult`). It is excluded from the offline drift guard. The gate must keep it out of the default `scripts/invoke-tests` registry-free run.
5. The seam does not change what `internal/cache` persists.

## Implementation Plan

1. Define a per-instance registry-client provider as the seam. Introduce a small interface in `internal/registry` covering the methods consumers actually use across `internal/cli` and `internal/modules` (`FetchIndex`, `Fetch`, `ModuleVersions`, `ResolveLatestVersion`, `Registry`). All five are consumed by code that becomes interface-typed after the rename — in particular `ModuleVersions` is called directly at `doctor_validate.go:564` and `:661`, so omitting it would fail to compile. The interface lives in `internal/registry` rather than `internal/cli` because it crosses package boundaries — `internal/modules` (`InstallModule`, `InstallRoleDependency`) consumes it too — and the "interfaces where consumed" rule does not cleanly apply when consumers span packages. Naming: rename the existing concrete `Client` struct to an unexported `client` (or `realClient`) and export `Client` as the interface — this is the idiomatic Go pattern (interface keeps the natural name; concrete becomes implementation detail) and avoids the `ClientInterface`/`IClient` anti-patterns. Every existing `*registry.Client` reference in the codebase becomes `registry.Client` (now an interface). Storage and access follow the existing `Flags` pattern verbatim: `Flags` is not a field on the cobra command — it is stored on the command's `context.Context` via a `flagsKey{}` context key and retrieved through `getFlags(cmd *cobra.Command) *Flags` (`internal/cli/start.go:25` / `:45`). Mirror that exactly: add a `providerKey{}` context key, a `WithProvider(ctx, provider)` constructor, and a `getProvider(cmd *cobra.Command) func() (registry.Client, error)` accessor; `NewRootCmd()` installs the production provider (a closure returning `registry.NewClient()`) into the root context, tests override the value bound to `providerKey{}` before invoking the command. This matches the repo's established factory pattern (`NewRootCmd()` builds isolated instances) so parallel tests do not race on shared global state, and it generalises beyond index acquisition to cover every registry interaction in the four target commands with one stub. Refactor `fetchIndex` to obtain its client through `getProvider(cmd)()` rather than calling `registry.NewClient()` directly.
2. Route the four target commands' inline client constructions through the provider, then propagate the interface type through the rest of the consumer chain. There are two distinct edit kinds; conflating them is the most common implementation mistake here.

   Kind A — route through provider. The inline `registry.NewClient()` call is replaced with `getProvider(cmd)()`. Limited to the four target commands' sites because only they need test-time stubbing for the drift guard:

   | File | Site |
   | ---- | ---- |
   | `internal/cli/modules_shared.go:27` | `fetchIndex` (covers `update` and `install` transitively) |
   | `internal/cli/search.go:167` | `runSearch` registry branch |
   | `internal/cli/library.go:68` | `runLibrary` client construction |
   | `internal/cli/doctor.go:218` | `fetchAndValidateSchemas` |
   | `internal/cli/doctor.go:274` | `resolveIndexVersion` fallback |

   Kind B — type cascade only. The function signature changes from `*registry.Client` to `registry.Client` (the new interface) so the codebase still compiles after Kind A's changes, but the inline `registry.NewClient()` call inside is left alone — these sites are out of scope for the offline drift guard. `list` is out of scope per Scope (registry only under `--verbose`, which the guard does not pass); `resolve.go`'s `ensureIndex` already has its own `skipRegistry` mechanism; `autosetup.go` is in `internal/orchestration` outside the four target commands. `doctor_validate.go` is carved out of provider routing (Kind A) and the offline drift guard (step 5), but it is **not** carved out of the rename — the `Client`→interface change is global, so its `*registry.Client` signatures must still cascade to the interface like any other Kind B site. Its inline `registry.NewClient()` at `:196` stays (the carve-out keeps `doctor validate` on the real registry):

   | File | Sites |
   | ---- | ----- |
   | `internal/cli/update.go` | `checkAndUpdate` parameter |
   | `internal/cli/install.go` | `installModule`, `installSingleModule` parameters |
   | `internal/cli/list.go` | `checkForUpdates` parameter; inline `registry.NewClient()` at `:154` stays |
   | `internal/cli/task.go` | `installTaskAndReloadEnv`, `installTaskFromRegistry` parameters |
   | `internal/cli/resolve.go` | `resolver.client` field, `autoInstall`, `ensureIndex`; inline `registry.NewClient()` at `:701` stays |
   | `internal/cli/doctor_validate.go` | `validateIndex`, `validateCheckIndexVersionExists`, `validateModules`, `validateOneModule` parameters (consume `ModuleVersions`/`Fetch`/`Registry`); inline `registry.NewClient()` at `:196` stays |
   | `internal/modules/install.go` | `InstallModule`, `InstallRoleDependency` parameters |
   | `internal/orchestration/autosetup.go` | `installDefaultModules` parameter; inline `registry.NewClient()` at `:61` stays |

   The Kind B breadth (around a dozen signatures across three packages, including the central `resolver`) is the bulk of the implementation effort, not the five routed sites in Kind A. Preserve `library`'s `--export` branch (it still needs `result.SourceDir` from `client.Fetch`) and `search`'s graceful fallback. `doctor`'s schema validation must still degrade to a "Skipped" section when the stub or the real registry signals unavailability, since the documented JSON shape for that section is reached through the existing graceful-fallback path.
3. Build the test fixture. Place the stub in an `internal/cli` test file (suggested `registry_stub_test.go`) so it is compiled only for tests. The stub implements `registry.Client` and dispatches by module path. The library index path must be served through two representations, because the four commands consume the index two different ways:

   - `search` and `update` go through `FetchIndex`, which returns a parsed `*registry.Index`. For these, the stub returns a canned in-memory `*registry.Index` (a builder with representative entries across agents/roles/contexts/tasks).
   - `library --json` does **not** consume a `*registry.Index`. Its path (library.go:79-109) is `ResolveLatestVersion` → `Fetch` → `printJSONIndex(SourceDir, client.Registry(), …)` → `registry.LoadIndex`, which runs `load.Instances` over CUE files on disk at `Fetch`'s `SourceDir`, using `client.Registry()` to resolve imports. For `library`, the stub's `Fetch` against the index path must therefore return `registry.FetchResult{SourceDir: <a temp dir of index CUE, incl. the sentinel agent>}`, and `Registry()` must return a value `LoadIndex` can use offline. The in-memory `*registry.Index` and the on-disk fixture must carry the same entries so the documented shapes agree.

   `Registry()` offline caveat: `LoadIndex` passes `client.Registry()` into `load.Config.Registry`. If the library index package imports any external module (for example the schemas module to constrain entries), an offline load needs that dependency resolvable without network — so the on-disk fixture's `index` package must be self-contained, or the stub must hand `LoadIndex` an offline/local registry. Verify the real index module's dependency surface before relying on a nil registry.

   A request against `registry.SchemaModulePath` returns an error so `doctor`'s schema-validation section deterministically falls through to "Skipped" — the documented JSON shape for that section is identical to the success-path shape and the error path avoids shipping a schema fixture. The stub's public surface holds a response table keyed by `(method, modulePath)` and a default for unknown keys, with constructor `newRegistryStub(idx *registry.Index, sourceDir string) *registryStub` (taking both the in-memory index for `FetchIndex` consumers and the on-disk fixture dir for `library`'s `Fetch`+`LoadIndex` path) plus mutators `stub.SetFetch(path string, result registry.FetchResult, err error)` / `stub.SetResolve(path string, version string, err error)` so per-test overrides remain possible without rebuilding the stub. Add a focused helper alongside `setupStartTestConfig` (signature: `func setupStartTestConfigWithRegistry(t *testing.T, idx *registry.Index) (tmpDir string, stub *registryStub)`) that performs the standard `setupStartTestConfig` isolation, writes an on-disk `index` CUE fixture derived from `idx` into a temp dir (so the in-memory index and the on-disk fixture stay in lockstep), and constructs the stub via `newRegistryStub(idx, fixtureDir)`, returning the tmp dir and stub. The helper does not build a `*cobra.Command` and does not inject the stub anywhere — provider injection is `captureJSON`'s responsibility (step 4), because that is where the command instance is constructed. Do not overload `setupStartTestConfig` itself, since most existing callers do not need the stub.
4. Add the JSON-mode capture helper. `snapshots_test.go` renders text only and pins byte-identical baselines, which is the wrong shape for the drift guard (the guard asserts structural keys and types, not bytes). Add a new test file `internal/cli/json_capture_test.go` rather than extending `snapshots_test.go`, since the two have different assertion strategies and bundling them invites confusion. The new file exposes one helper, signature: `func captureJSON(t *testing.T, stub *registryStub, args ...string) (decoded map[string]any, raw []byte)` — it builds a root command via `NewRootCmd()`, replaces the value bound to `providerKey{}` on `cmd.Context()` with a closure that returns `stub` (using `cmd.SetContext(WithProvider(cmd.Context(), func() (registry.Client, error) { return stub, nil }))`), sets `cmd.SetOut(&buf)` and `cmd.SetErr(io.Discard)`, runs `cmd.SetArgs(args)` and `cmd.Execute()`, fails the test if stdout does not decode as JSON, and returns both the decoded value (for keys-and-types assertions) and the raw bytes (for sentinel-substring assertions). Threading the stub through the parameter keeps the seam visible at every call site — a missing `stub` argument is a compile error, ruling out the silent-bypass failure mode the sentinel-agent acceptance criterion is designed to catch. The parent project's drift guard uses `captureJSON` once per `--json`-capable command to compare decoded keys/types against the documented schema in `help schemas`.
5. Carve out `doctor validate`. Add a build-tagged integration test using `//go:build registry` that runs `doctor validate --json` against the real registry and asserts the report shape. Build-tag over env-gate: tag exclusion keeps the file out of the default compile and the default `go test` discovery (no per-test `t.Skip` noise, no risk of an accidentally-set env var enabling network in CI), and it composes cleanly with `scripts/invoke-tests` which simply does not pass `-tags=registry`. Document the tag in the file's package comment; `AGENTS.md` documentation is owned by step 6 to keep that update in one place.
6. Update `AGENTS.md` and the parent project doc when this lands. In `AGENTS.md`: add the registry-client provider to "Testing key principles" (alongside the existing `skipRegistry` guidance) so future contributors know that new registry-touching code consumes the `registry.Client` interface through the provider; document `setupStartTestConfigWithRegistry` as the test entry point for offline registry-backed coverage and `captureJSON` as the JSON-capture runner; and document the `//go:build registry` tag as the opt-in for the `doctor validate` integration test. In `02-project-cli-contract-alignment.md`: Plan step 7 and Requirement 6 should describe the registry-client-provider seam and the `doctor validate` carve-out, and drop the incorrect `skipRegistry`/`internal/cache`-fixture description.

Decision left to the implementer: whether to instead build a full offline stub for `doctor validate`'s per-module fetch/validate walk (a second seam over `client.Fetch` and schema validation) and keep it in the offline drift guard. This is more faithful but materially more work and more brittle. The recommended path is the carve-out (step 5), because `doctor validate`'s output shape is simple and stable while its execution path is the most expensive to stub.

## Constraints

- Pure Go, gofmt-clean, `golangci-lint` clean. `scripts/invoke-tests` (lint + tests) must pass and must not reach the live registry.
- Follow the repo's Cobra patterns: command construction through `NewRootCmd()`, `RunE` returning errors. Do not introduce shared mutable global state that leaks across parallel tests; prefer per-instance injection consistent with the existing factory.
- Honour AGENTS.md testing principles: real behaviour over mocks where practical (real CUE validation, real files via `t.TempDir()`), interfaces/parameters over globals.
- No production behaviour change. The provider's default must return a real `registry.NewClient()` so every consumer (`fetchIndex` and its callers, `search`, `library`, and both of `doctor`'s registry sites) behaves exactly as today — including the `cache.WriteIndex` side effect from `fetchIndex` callers, `search`'s registry-unavailable fallback, and `doctor`'s schema-validation "Skipped" fallback.
- Provider lifecycle: the provider is shaped as `func() (registry.Client, error)` and is invoked once per registry interaction (a fresh client per call), not cached across calls. This preserves the current call count exactly — `doctor --json` still constructs two clients per invocation (one for the version resolve, one for the schema fetch), `search` still constructs one per invocation. Tests return the same stub instance from every invocation, so the call-count preservation has zero observable effect in tests; production sees identical `registry.NewClient()` semantics to today.

## Acceptance Criteria

- `library --json`, `search --json`, `update --json`, and `doctor --json` run to completion offline in tests against an injected stub client and emit their documented shapes; no test in the default pipeline contacts the live registry. `doctor`'s schema-validation section is covered by the same stub: the stub returns an error for `registry.SchemaModulePath` so the section deterministically renders the "Skipped" branch shape (matching step 3's chosen path).
- Running the same commands without the stub still fetches from the registry exactly as before (manually verifiable; `cache.WriteIndex` still fires from `fetchIndex` callers; `doctor`'s `resolveIndexVersion` still reads cache without writing; `search` still degrades gracefully when the registry is unreachable; `doctor`'s schema-validation section still degrades to "Skipped" when the registry is unreachable).
- `doctor validate --json` shape is asserted by an integration test that is excluded from the default registry-free run and gated explicitly.
- The JSON-capture harness exists and is usable by the parent project's `help schemas` drift guard. End-to-end validation of the harness is deferred to the parent project: this project ships the seam, the stub, the helper, and the JSON-capture extension to the snapshot pattern, but the drift-guard tests that exercise all four commands through the harness are written in `02-project-cli-contract-alignment.md`. A smoke test in this project proves the wiring end-to-end by asserting that a uniquely-named entry placed into the stub's index fixture (for example, an agent named `stub-sentinel-agent`, present in both the in-memory index and the on-disk fixture `library` loads from) appears in the captured `library --json` output. This proves the stub was consulted — a real registry would never carry the sentinel name — and rules out a silent bypass of the provider seam.
