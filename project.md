# Project: Split Index Access Into Cache-Gated Display and Live Install Paths

## Goal

Establish one clear rule for how commands read the library index from the CUE Central Registry: read-only display commands consult the local 24-hour cache and run offline when the index is unchanged; every command that installs a module or checks for newer versions resolves live against the registry so it never acts on a stale view. Today the line is inconsistent — display commands hit the registry on every invocation while the auto-install resolution path can act on a stale cache and miss a freshly published module.

The two halves — cache-gating display and going live on install/resolve — ship together because they are one rule, not two features: both are built on a single extracted cache-gating primitive (Requirement 1, consumed by both the display helper and `ensureIndex`), and both are overridden by the one persistent `--refresh` flag. The display half's payoff is offline operation on a fresh cache and consistency with the rule, not a raw speed win; the resolution half's payoff is correctness (a module published within the cache window stays discoverable). Splitting them would duplicate the shared primitive and fragment the shared flag.

## Scope

In scope:

- Cache-gate the read-only display commands: `start list`, `start search`, and `start library` (default).
- A new persistent `--refresh` flag, meaning "bypass the 24h index cache and resolve the index live," honoured by every index-reading surface. On the display commands (`list --verbose`, `search`, `library`) it bypasses the cache read across all output modes (default, `--json`, `--export`). On the resolution surfaces (`start`, `task`, `--role`, `--context`, `--agent`, `get`, `describe`) it forces `wantLive` true even for an installed match, giving an on-demand override of the cache-gated path — including the accepted twin-staleness limitation on `get`/`describe`. On the already-live commands (`install`, `update`, `doctor validate`) it is a harmless no-op. It is the single user-facing override of the project's cache-gating rule, replacing what would otherwise be a per-command flag on each surface.
- Make the resolution / auto-install path live when, and only when, some surface in the invocation has no installed match, via one up-front decision shared by the whole resolver. `internal/cli/resolve.go` `ensureIndex` currently short-circuits on a fresh cache for every caller; instead, force a live resolve when any pending surface found no installed module to satisfy it, so a name about to be auto-installed (`start`, `start task`, `--role`, `--context`, `--agent`, and the cross-category `start get` / `start describe`) is resolved against the latest index, consistent with `start install`. An invocation whose every surface is satisfied by an installed module stays cache-gated.
- A new cache-gating helper for the display commands.

Out of scope:

- `start install`, `start update`, `start doctor validate`. All already resolve live; unchanged.
- The shared `fetchIndex` helper in `internal/cli/modules_shared.go`. Both its callers (`install`, `update`) resolve live, so it is unchanged.
- `start doctor` index-version resolution, which is already cache-first display.
- First-run auto-setup (`internal/orchestration/autosetup.go`). Nothing is cached on first run, so it must fetch.
- The CUE module cache (content storage). This project changes only how the index version is resolved, not how module content is cached.
- The `registry.Client` interface and the `cache` package public API.

## Current State

Every index access flows through `client.FetchIndex(indexPath)`, which performs two registry operations:

1. `ResolveLatestVersion` — metadata only (an OCI tag-list via `ModuleVersions`). It short-circuits with no network call when handed an already-canonical version (e.g. `...@v1.14.0`), but makes the metadata call when handed a bare major (e.g. `...@v1`).
2. `Fetch` — content. Served from CUE's local module cache when that version was pulled before; network only for a version not yet downloaded.

The `start` index cache lives at `cache.cue` in the XDG cache dir (`internal/cache/cache.go`). It records `index_version` (canonical) and `index_updated`. `IndexCache.IsFresh` returns true within `DefaultMaxAge` (24h). Passing `FetchIndex` a cached canonical version makes the call fully offline when unchanged; passing a bare major forces the metadata call.

Two distinct behaviours exist today, and both are being corrected:

- `internal/cli/resolve.go` `ensureIndex` (lines ~266-321) reads the cache, checks `IsFresh`, guards that the cached version belongs to the same module as the configured index path (`modules.ModuleFromOrigin`), and on a fresh hit passes the canonical version to `FetchIndex` for an offline resolve; on a miss it fetches and writes the cache. This cache-gating is correct except in one case: when resolution found no installed match and is about to auto-install, a fresh cache can hide a module published in the last 24h. The cache-gating decision inline here is extracted into a shared primitive that both this branch and the new display helper consume (Requirement 1).
- `start search` (`search.go:167`) and `start library` (`library.go:75,85`) bypass the cache and call the registry on every invocation, firing a metadata request each time. `start list` is the same but gated: its only registry access, `checkForUpdates` (`list.go:148` -> `list.go:275`), runs solely under `--verbose` (`list.go:142`), so plain `start list` and `start list --json` already make no registry call — the cache-gating change is observable only on `start list --verbose`. All three should become cache-gated. Note `library` does not use `FetchIndex`; it calls `ResolveLatestVersion` then `Fetch` directly and reads `result.SourceDir` (library.go:75,85,101,103,105), so routing it through the helper means feeding the helper's resolved version into a `Fetch` for `SourceDir`, not swapping in `FetchIndex`.

The governing rule is "resolve live when a surface in this invocation has no installed match; otherwise cache-gated." A `start` invocation holds one resolver and one shared index: `ensureIndex` is memoized via `didFetch`, so the first call fetches and every later call returns the held index, and that single index serves agent, role, context, and task alike. Liveness is therefore one decision per invocation, not one per surface. Most surface names are known up front — `flags.Agent`, `flags.Role`, `flags.Context`/`selection.Tags`, and the task arg are all in hand before the first `r.resolve*()` call — so the bulk of the decision is computed once, before any resolve runs, as a union over those pending surfaces: live iff any of them has no installed match under either the exact or the fallback mode (all network-free `collectInstalled` lookups). One surface is the exception. `start task` resolves a task-declared role whose name is not a flag: it is read from the task's own content (`orchestration.GetTaskRole`, `task.go:184`) only after the task itself has resolved, with the config reloaded mid-sequence around each install (`task.go:168`, `task.go:189`; the resolver documents the flags → task → task-role stages at `resolve.go:50-55`). That name does not exist when the union is computed, so the task-declared role cannot join it and instead carries a targeted late liveness check. See Requirement 4.

Two structural points follow:

- The category-specific exact tier can skip the index entirely: a single installed exact match returns before `ensureIndex` is called (`resolveExact`, `engine.go:150`), so that case makes no registry call at all. This is an optimisation, independent of the liveness decision.
- Every other path reaches `ensureIndex` and uses the held index: the category-specific fallback (substring) tier (`resolveFallback`, `engine.go:196`) consults it to merge registry matches even when it already has an installed substring match, and the cross-category surfaces (`get`, `describe`) never short-circuit because they consult it even for an installed name to detect a same-name twin in another category.

Computing the decision up front as a union — rather than per-surface, late, from the partial installed set visible at each `ensureIndex` call site — forces live exactly when an auto-install may occur (any surface in the invocation has no installed match) while keeping a wholly-installed invocation cache-gated. It is position-independent: a surface's resolution does not depend on where it falls in the agent → role → context → task order. The earlier per-surface-with-upgrade approach was rejected for this reason; see Requirement 4.

Cache-gating an installed `get`/`describe` query carries one accepted limitation. The cross-category surfaces consult the index for the installed name to detect a same-name twin in another category, and under cache-gating that detection runs over the cached index, so a twin published into another category within the cache window (<24h, fresh cache only) may not surface until the cache refreshes. This is deliberate, not an oversight. `get`/`describe` mirror the resolution the category-specific surfaces would perform — the module they show is the module that surface would use — and a category-specific surface uses an installed module with no freshness pull at all (it short-circuits offline at `engine.go:150` and never checks for a newer version). Cache-gating the installed `get`/`describe` case is therefore the faithful choice: resolving it live would make `get`/`describe` less like the command they predict, not more. Twin detection is informational, never install-triggering, so the missed-twin window only withholds a disambiguation notice and never resolves or installs the wrong module. The window is narrow by construction — it requires an installed exact, a fresh cache, and a twin published after that cache was written; a stale or missing cache refetches and catches the twin, and an uninstalled name resolves live anyway. A user who suspects a fresh twin can force a live resolve with the persistent `--refresh` flag (Requirement 3), so the limitation is overridable on demand.

The auto-installed module's version is already resolved live independently of the index: `autoInstall` -> `modules.InstallModule` calls `ResolveLatestVersion` on the module path (`modules/install.go:36`). A stale index therefore never installs an outdated version; its only failure mode is making a newly-published module undiscoverable. The liveness fix targets exactly that discoverability gap.

`fetchIndex` in `modules_shared.go` is shared by `install` and `update`. It calls `FetchIndex(resolveLibraryIndexPath())` with no cache read, then writes the cache best-effort. Both callers resolve live, so this helper is unchanged.

Desired end state per command:

| Command | Reads 24h cache? | Rationale |
| --- | --- | --- |
| resolution, any surface has no installed match (`task`, `--role`, `--context`, `--agent`, `get`, `describe`) | no (change to live) | About to auto-install; the whole invocation must see the latest, like `install`. |
| resolution, every surface satisfied by an installed module | yes (cache-gated), unless `--refresh` | Category-specific exact match skips the index entirely; fallback-matched and `get`/`describe` queries reach `ensureIndex` but read the cache — no freshness need when already on disk. `--refresh` forces live. |
| `start list --verbose` | yes (change), unless `--refresh` | Read-only update-available display (registry access is `--verbose`-only); 24h staleness is fine. |
| `start search` | yes (change), unless `--refresh` | Discovery over the index; same tolerance. |
| `start library` | yes (change), unless `--refresh` | Displays rarely-changing library data. |
| `start install` | no (already live) | Must install the latest; a stale index could hide a new module or version. |
| `start update` | no (already live) | Its job is to detect newer versions; must see live metadata. |
| `start doctor validate` | no (already live) | Maintainer consistency check; wants live truth. |
| `start doctor` (index ver) | yes (already cache-first) | Display only. |
| auto-setup | no (first run) | Nothing cached on first run. |

The line that results: live only when a resolve may auto-install a not-yet-installed module; cache-gated for everything else — pure display and any resolve already satisfied on disk.

## Requirements

1. A cache-gating helper that resolves the effective index version for the display commands. Its shared job is the version decision, not the output shape: given an effective index path and a client, it yields the canonical version to use — the fresh cached version when one is available, otherwise the latest resolved from the registry, writing the cache best-effort on a refresh. It must honour `IsFresh` against `DefaultMaxAge` and verify the cached version belongs to the same module as the effective index path (`modules.ModuleFromOrigin`) before reuse. Callers fetch from that version what they each need: `list` and `search` consume the parsed `*Index`; `library` needs the fetched module's source directory (`SourceDir`) for `--export` (raw CUE), `--json`, and the default view, all of which read from disk. The helper must serve both consumers — do not pin it to returning only a parsed `*Index`.

   The cache-gating decision itself — read cache, `IsFresh` against `DefaultMaxAge`, the `ModuleFromOrigin` module-match guard, and the cached-canonical-vs-live-resolve choice — must live in exactly one place, consistent with this project's "one clear rule" goal. Extract that decision into a single primitive and have both the display helper and `ensureIndex`'s cache-gated branch consume it, rather than re-implementing the logic in the helper. The primitive answers "which version, and was it served fresh from cache or freshly resolved"; the display helper wraps it with the best-effort cache write and the display commands' fetch, while `ensureIndex` wraps it with `wantLive`, memoization, graceful degradation, and the parsed-index return. Do not copy `ensureIndex`'s inline logic into the helper. (`doctor.resolveIndexVersion` keeps its deliberately freshness-blind "show whatever is cached" behaviour and is out of scope; route it through the primitive only if it falls out cleanly.)

2. `start list` (under `--verbose`, its only registry-touching mode) and `start search` resolve the index through the cache-gating helper. With a fresh cache they make no registry metadata request.

3. `start library` resolves through the cache-gating helper by default. A persistent `--refresh` flag, registered once on the root command, forces a live index pull bypassing the cache read wherever the index is read. On `library` it is honoured across all output modes: default, `--json`, and `--export`; on `list --verbose` and `search` it likewise bypasses the cache read; on the resolution surfaces it forces `wantLive` true (see Requirement 4). After any `--refresh` pull the cache is updated so subsequent commands see the freshly pulled version. On the already-live commands (`install`, `update`, `doctor validate`) the flag is a no-op.

4. Resolution resolves the index live when any surface in the invocation has no installed match, and cache-gated otherwise. The decision is made once per resolver, up front, and shared by every surface — not recomputed per surface, with one bounded exception for the late-bound task-declared role (below). When no installed module satisfies some surface — on any surface, including the cross-category `get`/`describe` — the shared index is resolved live so a module published within the last 24h is discoverable and auto-installed. When every surface is satisfied by an installed module, resolution stays cache-gated: the category-specific exact tier skips `ensureIndex` entirely, while the category-specific fallback tier and `get`/`describe` reach `ensureIndex` and read the held cache-gated index. Cache-gating an installed `get`/`describe` query means its cross-category twin detection runs over the cached index; the resulting accepted limitation (a twin published into another category within the cache window may not surface until refresh) is documented in Current State and is by design, since `get`/`describe` mirror what a category-specific surface would use and that surface consults no freshness for an installed module.

   The decision is a single up-front union, computed before the first resolve runs:

   - `ensureIndex` is memoized via `didFetch`: it does real work only on its first call per resolver, and later calls return the already-fetched index. One index serves the whole invocation. The liveness choice is therefore one decision for the resolver, fixed before any surface resolves.
   - The flag- and arg-bound surface names are known before resolution begins — the multi-stage drivers (`task.go:93`, `start.go:374`) read `flags.Agent`, `flags.Role`, `flags.Context`/`selection.Tags`, and the task arg up front. Compute `wantLive` once from the union over those pending surfaces: live iff any lacks an installed match under both the exact and the fallback mode (network-free `collectInstalled` lookups), and pass it into `ensureIndex`. A wholly-installed invocation is cache-gated; one with any no-installed-match surface forces live. The persistent `--refresh` flag ORs into the union (`wantLive = anyNoInstalledMatch || flags.Refresh`), so a user can force a live resolve even when every surface has an installed match — the on-demand override of the cache-gated path, including the accepted `get`/`describe` twin-staleness limitation.
   - One surface is late-bound and excluded from the up-front union: the task-declared role. `executeTask` reads it from the resolved task's content (`GetTaskRole`, `task.go:184`) only after the task surface resolves, with the config reloaded around each install (`task.go:168`, `task.go:189`), so its name does not exist when the union is computed. It therefore carries a targeted late liveness check: after the task resolves, if a declared role is present and has no installed match (network-free `collectInstalled` under both modes) while the up-front union resolved cache-gated (`wantLive` false), force a one-time live re-resolve before resolving the role, so a role published within the cache window is discovered and auto-installed. The check keys off the stored `wantLive`, not a new held-index-liveness field, so the "single `didFetch` suffices / no `indexLive` field" stance holds; in the rare case the cache-gated path had already fetched live for a stale cache it repeats at most one metadata resolve, which is preferred to tracking whether the held index was actually cache-served. This is the sole permitted per-surface upgrade — confined to the one surface whose name is structurally unavailable up front — and is not the rejected general per-surface design, which re-evaluated liveness for every surface at its own call site. When the up-front union already forced live (any flag/arg surface had no installed match, including the common case of an uninstalled task) or `--refresh` is set, the held index is already live and the late check is a no-op.
   - `wantLive` true takes the effective bare-major path to `FetchIndex` (a live resolve); `wantLive` false keeps the cache-gated path (cached canonical version when fresh, otherwise a fetch). Because the union decision is fixed before the first resolve, the up-front surfaces need no per-surface upgrade or re-resolve; the held index is reclassified mid-invocation only by the single bounded late check for the task-declared role above. The earlier per-surface-with-upgrade design was rejected for the general case: it never downgrades, so what it actually implements is the position-dependent rule "live iff this surface or any earlier surface in the fixed order has no installed match" — a less principled semantic that required a three-state held index (live / cache-gated / injected), an upgrade-on-success path for every surface, and "never overwrite a good cached index with nil" handling. The up-front union eliminates that for all up-front-known surfaces while making their resolution independent of position; the lone late check is the minimal, surface-specific exception forced by a name that does not exist until the task content is read.

   The injected-index test seam (`newResolverWithIndex`) keeps its short-circuit at the top of `ensureIndex` so injected-index tests stay offline (several resolve registry-only, no-installed-match queries with `r.client` left nil and would otherwise resolve live and break). Injection and real-fetch memoization share the one `didFetch` field, distinguished only by when it is set — injection sets it at construction, the real fetch during the first call — so the single `if r.didFetch` short-circuit serves both; an injected resolver returns its index ahead of, and is never subject to, the `wantLive` decision.

   `ensureIndex` must keep its graceful degradation (return a nil index with the failure recorded in `indexErr` when the registry is unavailable) and its best-effort cache write on any live resolve.

5. `start install`, `start update`, and `start doctor validate` continue to resolve the index live on every invocation, unchanged. `fetchIndex` is unchanged.

6. Target-module content fetches are unchanged. `install` and `update` still fetch the requested module's content after the index lookup; this project changes only index version resolution.

7. Cache-miss and different-module behaviour is preserved for the display path. A missing or stale (>24h) cache, or a cache whose version belongs to a different module than the current effective index path, triggers a single fetch and a cache write.

## Constraints

- Go, matching the repository's current toolchain. Build with `go build ./...`.
- Do not alter the `registry.Client` interface or the `cache` package's public API unless strictly required; prefer reusing `cache.ReadIndex`, `cache.WriteIndex`, `IndexCache.IsFresh`, and `cache.DefaultMaxAge`.
- Preserve graceful degradation. Registry unavailability must remain non-fatal where it currently is (the resolver returns a nil index with the failure recorded; `search` records `registryErr` and degrades). Cache writes remain best-effort and debug-logged only.
- Preserve the module-match guard (`modules.ModuleFromOrigin`) so a changed `library_index` setting invalidates cache reuse.
- Keep user-facing output semantics honest: a progress or debug line that signals a network resolve must reflect whether one actually happened. `ensureIndex`'s "Fetching registry index..." line should show when it resolves live (the invocation has a no-installed-match surface, or `--refresh` is set) and not when it serves from a fresh cache.
- Follow the registry-client seam guidance in AGENTS.md: command paths obtain the client through `getProvider(cmd)()`; the resolver and auto-setup remain on their direct `registry.NewClient()` paths.

## Implementation Plan

1. Extract the cache-gating decision (cache read / `IsFresh` / module-match-guard / cached-canonical-vs-live choice) currently inline in `ensureIndex` into a single shared primitive, then build the display helper described in requirement 1 on top of it and refactor `ensureIndex`'s cache-gated branch to call the same primitive. One definition of the rule, two consumers — not a copy in each.

2. Make `ensureIndex` resolve live only when some surface in the invocation has no installed match. Compute `wantLive` once, up front, before the first resolve: in the multi-stage drivers (`task.go`, `start.go`) the agent, role-flag, context, and task names are all known before any `r.resolve*()` call, so take the union over those pending surfaces — live iff any lacks an installed match under both the exact and the fallback mode (network-free `collectInstalled` lookups) — and store it on the resolver for `ensureIndex` to read. Do not key the decision on a single surface's exact-tier installed set, which is empty for a fallback substring-installed query and would force a spurious live resolve. OR `flags.Refresh` into the union. `wantLive` true takes the effective bare-major path to `FetchIndex`; false keeps the existing cache-gated path. Handle the one late-bound surface separately: after the task resolves, if `GetTaskRole` returns a declared role with no installed match while the up-front union resolved cache-gated (`wantLive` false), force a single live re-resolve before resolving that role — the only per-surface upgrade, confined to the surface whose name does not exist until the task content is read. Key it off the stored `wantLive`, not a new held-index-liveness field, so the "single `didFetch` suffices" stance holds; it may repeat at most one metadata resolve when the cache-gated path had already fetched live for a stale cache. For the up-front surfaces the existing single `didFetch` memoization suffices — no `indexLive` field, no per-surface upgrade/re-resolve, and no "don't overwrite with nil" handling; the held index is reclassified only by that lone late check. Keep the injected-index seam's short-circuit at the top of `ensureIndex` (it is offline and outside the `wantLive` decision), the graceful fallback, the conditional progress/debug line (shown only on a live resolve), and the best-effort cache write on a live resolve.

3. Route `start list` (`checkForUpdates`) and `start search` through the cache-gating helper. For `start library`, feed the helper's resolved version into a `Fetch` for `result.SourceDir` rather than swapping in `FetchIndex`. Leave `fetchIndex` (and therefore `install` and `update`) unchanged.

4. Register a persistent `--refresh` flag on the root command, default false, in the persistent `Flags` struct so every surface reads one value. When set, the display commands (`library`, `search`, `list --verbose`) bypass the cache-gating helper's cache read and resolve live; apply this before the output-mode branch so `library`'s default, `--json`, and `--export` all honour it. On the resolution surfaces, OR the flag into `wantLive` (step 2) so an installed-match query resolves live too. Update the cache after any live pull. On `install`, `update`, and `doctor validate` the flag is inert (they already resolve live). Document the flag in the root command's persistent-flag help.

5. Update AGENTS.md where it describes index/cache and resolution behaviour and the command listings, so the cache-gated display commands, the now-live resolution path, and the new persistent `--refresh` flag (added to the Persistent Flags table) are documented.

6. Add a metadata-resolve observable to the test seams, shared across the resolver and display paths. Both the resolver-path and the display-command tests must assert "no metadata resolve happened", and neither existing seam can yet show it: the resolver short-circuits ahead of the decision, and the display stub (`registryStub`) exposes only `providerCalls`, which counts provider hand-outs and is `1` on both the fresh-cache and stale-cache paths (a client is obtained either way to fetch the index content), so it cannot distinguish cache-gated from live. Add a single metadata-resolve observable — a counter on `ResolveLatestVersion` and/or a record of the path `FetchIndex`/`Fetch` was asked for, so a bare-major (live) request is distinguishable from a canonical cached (cache-gated) one — and expose it on both:

   - A single test-only recording registry client injectable on the resolver, parallel to `skipRegistry`. When set, `ensureIndex` runs its full cache/`wantLive` decision and then resolves through this client instead of constructing one via `registry.NewClient()`, recording the bare-major (live) vs canonical (cache-gated) path. This one seam also supplies the index for the decision-runs case: the stub's `FetchIndex` return is the injected index, fed through the live decision, so no separate "inject an index without tripping the `didFetch` short-circuit" affordance is needed. It is a test hook only — the resolver keeps `registry.NewClient()` in production, so the AGENTS.md seam guidance is unchanged. It is required because the two existing offline resolver seams both short-circuit ahead of the decision under test: `skipRegistry` returns nil before the cache read, and the injected-index seam (`newResolverWithIndex`) sets `didFetch` at construction so the single `if r.didFetch` short-circuit at the top of `ensureIndex` returns the injected index before the cache/`wantLive` logic runs (injection and real-fetch memoization share that one field, differing only in when it is set; see Requirement 4). Neither can observe which path the resolver took or the index it ends up holding. This brings the resolver to three test affordances (`skipRegistry`, `newResolverWithIndex`, the recording client); the broader smell of one struct carrying several injection/observation points is acknowledged but the structural refactor to dissolve it is out of scope for this project.
   - The same recording capability on the existing display-command stub used by the `--json` harness, so the display tests assert on the metadata-resolve count rather than the vacuous `providerCalls`.

7. Add or extend tests covering: a fresh-cache invocation of `list`/`search`/`library` performing no metadata resolve; a stale/missing cache triggering one fetch and a cache write on a display command; `--refresh` forcing a live resolve regardless of cache freshness on a display command (`library`/`search`) and on a resolution surface with an installed match (e.g. `get`/`describe` of an installed module under `--refresh` pulls live); resolution of a no-installed-match query resolving live even with a fresh cache; resolution of an installed-match query staying cache-gated (category-specific exact makes no call; a fallback substring-installed query — e.g. `--role expert` resolving to an installed `go-expert` — and `get`/`describe` of an installed module serve from a fresh cache with no metadata resolve); a multi-stage resolve (`start --context <substring-installed> task <uninstalled>`) where one surface is substring-installed and another has no installed match resolves the whole invocation live from the single up-front union — so the uninstalled candidate is auto-installed regardless of surface order (a position-independence assertion: the same mix resolves live whether the uninstalled surface comes first or last); a `start task` whose task is installed but whose task-declared role is uninstalled resolves that role live via the late liveness check even though the up-front union was cache-gated, and the same case stays a no-op extra-pull when the union already forced live; and a `wantLive` invocation whose live resolve hits a transient registry error degrades gracefully to a nil index with `indexErr` set, exactly as any live-resolve failure does. Observation seams: display-command assertions use the existing offline `--json` harness (`setupStartTestConfigWithRegistry`, `captureJSON`) with the step-6 metadata-resolve observable on its stub client (not `providerCalls`, which is `1` on both cache-gated and live paths and proves nothing here); resolver-path outcome assertions use the recording resolver client from step 6 to observe the bare-major-vs-canonical path and the held index; the `ensureIndex` progress-line honesty (live-attempted vs cache-served) is asserted via the `"Fetching registry index..."` / `--debug` proxy.

## Acceptance Criteria

- With a fresh (<24h) cache whose version matches the configured index module, `start list --verbose`, `start search`, and `start library` (without `--refresh`) complete without a registry metadata resolve, observable via `--debug` output or the stub's metadata-resolve count from the test seam in Implementation Plan step 6 (not `providerCalls`, which does not distinguish cache-gated from live). (Plain `start list` makes no registry call in any case, so the list assertion must be tested against `--verbose`.)
- `--refresh` performs a live index resolve even when the cache is fresh, and updates the cache afterward: on `start library` across default, `--json`, and `--export` modes; on `start search` and `start list --verbose`; and on the resolution surfaces, where it forces a live resolve even for an installed-match query (overriding the cache-gated path, including the accepted `get`/`describe` twin-staleness limitation).
- Resolving a name with no installed match (e.g. `start task foo`, `start --role foo`, `start describe foo` for an uninstalled `foo`) performs a live index resolve regardless of cache freshness, so a module published within the cache window is found and auto-installed — matching `start install`.
- Running `start task <installed-task>` whose task-declared role has no installed match resolves that role live even when every flag/arg surface is installed and the cache is fresh, so a role published within the cache window is discovered and auto-installed; when any flag/arg surface already forced a live resolve (or `--refresh` is set), the role resolves against that same live index with no extra pull.
- Resolving a name satisfied by an installed module does not pull the index live: a category-specific exact match makes no registry call at all, and any other installed-match resolution (category-specific fallback, or `get`/`describe` of an installed module) serves from a fresh cache with no metadata resolve. For an installed `get`/`describe` query this means cross-category twin detection runs over the cached index, not a live pull — the accepted limitation documented in Current State.
- `start install`, `start update`, and `start doctor validate` perform a live index resolve on every invocation, unchanged from current behaviour.
- A missing or stale cache causes exactly one index fetch followed by a cache write on the affected display command.
- `--refresh` is a persistent flag, accepted by every command and listed in the Persistent Flags table; it forces a live resolve on the display and resolution surfaces and is an inert no-op on the already-live commands (`install`, `update`, `doctor validate`).
- AGENTS.md reflects the cache-gated display commands, the live resolution path, and the new persistent `--refresh` flag.
